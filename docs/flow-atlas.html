01 · PlatformSystem map

Three long-running processes plus two Next.js frontends. Chat and voice enter through different processes on purpose — Contract A1 keeps realtime audio off the API's event loop, because a slow LLM call in a request handler head-of-line blocks audio frames. Both processes run the same LangGraph turn from packages/ai.

02 · PlatformPackage layering contract

Imports flow one way, and tools/check_layering.py fails CI when they don't. Vendor SDKs are quarantined in providers/ so an engine swap (say, replacing Pipecat) touches one package.

03 · ConversationA chat turn, end to end

The shape worth internalizing: POST /messages returns 202 immediately — it only persists the user turn and stashes it in Redis. One long-lived SSE stream per conversation polls that stash every 250 ms and runs the turn. Persistence of the assistant's reply is wrapped in asyncio.shield, so a browser disconnect mid-stream can't lose the turn.

04 · ConversationThe agent graph

The manifest compiles into a hub-and-spoke LangGraph: every non-terminal agent re-enters __guard, which enforces budgets before the router picks the next hop. Routing is a constrained text completion, not a tool call — and two structural overrides outrank the model's choice: a named destination is authoritative, and an announced handoff is forced through.

05 · ConversationTicket & session lifecycle

Widgets never hold credentials — they hold a 20-second, single-use ticket bound to one conversation. Chat exchanges it for a 30-minute session; voice spends it on the WebRTC offer and gets no session at all.

06 · VoiceA voice call — WebRTC to Deepgram

No telephony provider is wired yet — live voice is browser WebRTC into apps/media. The widget asks for the microphone before any network call, so a refusal never creates a conversation row. The Pipecat pipeline turns audio into text, hands it to the same graph as chat, and speaks the reply.

07 · VoiceVoice vs chat pacing — the one deliberate asymmetry

Both channels produce a preamble ("One moment…") when a tool round starts. Chat renders it instantly — text costs nothing. Voice owns a single audio channel, so the preamble and the reply must be sequenced, or the caller hears one run-on sentence. That sequencing lives only on the call path.

08 · BookingBooking a slot

The engine, not the model, owns time. check_availability returns exactly one slot behind an opaque handle; book_appointment only accepts that handle, and the handle's stored instant wins over any time the model composed. The last line of defense is a database exclusion constraint — the only place double-booking can actually be prevented under concurrency.

09 · DataData model

Four migrations. Every foreign key is composite (tenant_id, id), so a cross-tenant reference is impossible by construction. Conversations and turns are partitioned monthly; the diary is the bookings tables — there is no external calendar.

10 · DataTenancy: the RLS request path

The database is the control; the service layer only re-checks. The runtime role can't bypass RLS even with a bug in every layer above it — and an unset tenant GUC matches no rows, so the system fails closed rather than open.

11 · VerificationThe harnesses

Every booking bug in this repo's history looked fine in the transcript and wrong in the row — so the harnesses assert against the database, never the chat. And because three fixes in a row each repaired one channel while breaking the other, chat and voice each have their own harness: run both.
